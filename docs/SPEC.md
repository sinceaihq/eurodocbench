# EuroDocBench specification (v0.1)

EuroDocBench measures how well a document-understanding system extracts the
key fields of **European business invoices** and returns them in a
**canonical, machine-readable form**, across 12 locales whose number, date
and currency conventions differ.

The benchmark is fully synthetic and generated by code in this repository,
so every label is exact, the data contains no real companies, people or bank
accounts, and new test sets can be generated at will.

## 1. Task

Input: one single-page invoice, given as

* **text track** — the PDF text layer (born-digital documents), or
* **scan track** — a JPEG of a simulated office scan (150 dpi, greyscale).

Systems may also use the original PDF. Output: the 12 fields below, in
canonical form.

| field | canonical form | may be empty |
|---|---|---|
| `invoice_number` | as printed (compared without spaces, case-insensitive) | no |
| `issue_date` | ISO 8601 date `YYYY-MM-DD` | no |
| `due_date` | ISO 8601 date | yes (~15 %) |
| `currency` | ISO 4217 code: `EUR`, `SEK`, `DKK`, `PLN`, `CZK` | no |
| `seller_name` | legal name of the issuer as printed | no |
| `seller_vat_id` | EU VAT number with country prefix, no spaces | no |
| `buyer_name` | legal name of the customer as printed | no |
| `buyer_vat_id` | EU VAT number | yes (~40 %) |
| `iban` | IBAN without spaces | yes (~10 %) |
| `net_amount` | total before VAT, plain decimal, `.` as decimal mark, no grouping | no |
| `vat_amount` | total VAT over all rates, plain decimal | no |
| `total_amount` | total including VAT, plain decimal | no |

Converting "1 234,56 €", "€1,234.56" or "5. března 2026" into `1234.56` and
`2026-03-05` is **part of the task**: these conversions are where
general-purpose systems fail on European documents.

Invoices with two VAT rates print one VAT line per rate and no VAT total
(as many real invoices do); `vat_amount` is then the sum of those lines.

## 2. Documents

| dimension | values |
|---|---|
| locales | `fi-FI`, `sv-SE`, `de-DE`, `fr-FR`, `nl-NL`, `it-IT`, `es-ES`, `pl-PL`, `pt-PT`, `cs-CZ`, `da-DK`, `en-IE` |
| layouts | `classic` (letterhead), `modern` (banded header, meta boxes), `compact` (label: value list), `grid` (bordered meta grid), `narrow` (receipt-style, monospace) |
| fonts | Liberation Sans / Serif / Mono |
| decimal mark | comma (11 locales), point (`en-IE`) |
| grouping | space, narrow no-break space (`fr-FR`), point, comma |
| dates | `d.m.yyyy`, `dd.mm.yyyy`, `dd/mm/yyyy`, `dd-mm-yyyy`, `yyyy-mm-dd`, `d. m. yyyy`; 20 % in long form with month names (`5. maaliskuuta 2026`, `5 de março de 2026`) |
| currency display | symbol (`€`, `kr`, `kr.`, `zł`, `Kč`) before or after the amount, or ISO code (30 %) |
| VAT | 2026 standard and reduced rates per country; 30 % of documents in countries with a reduced rate have two rates and a breakdown |
| labels | two label variants per field and language (e.g. *Rechnungsnummer* / *Rechnungs-Nr.*) |
| identifiers | VAT numbers in national format, 25 % printed with spaces; IBANs grouped by four in 70 % |

Every document is generated from a seeded random generator keyed by its id;
the same id and seed always yield byte-identical PDFs.

### Synthetic identities

Company and street names are built from invented syllables plus a sector word
and a legal form ("Velmora Logistik GmbH"); cities are real. **VAT numbers and
IBANs have the correct national format but deliberately fail their official
check digits**, so they cannot belong to a real company or account. The test
suite verifies this against the independent `python-stdnum` validators. No
personal names appear.

## 3. Splits (v0.1)

| split | documents | per locale × layout | seed |
|---|---|---|---|
| dev | 240 | 4 | 2026 |
| test | 1,200 | 20 | 2026 |

`dev` is for development and prompt/rule tuning. Report results on `test`.
Because the generator is public, a model could be trained on documents
generated with the published seed; such results must be labelled as
*trained on in-distribution synthetic data*. For contamination-free
comparisons, generate a fresh test set with an unpublished seed:

```bash
eurodocbench-generate --out private --seed <secret> --dev 0 --test 20
```

## 4. Scoring

`eurodocbench-score --gold gold/test.jsonl --pred predictions.jsonl`

Prediction file: JSON Lines, one `{"id": ..., "fields": {...}}` per document.
Unknown or duplicate ids are errors. A missing document counts as all-empty.

Per field, a prediction is **correct** when, after canonicalisation:

* amounts: both parse as plain decimals and differ by at most 0.005;
  a value such as `"1.234,56"` is a format error, not a near miss;
* dates: identical ISO strings;
* VAT numbers / IBAN: identical after removing spaces, dots and dashes,
  upper-cased;
* names: identical after NFKC, case folding and whitespace normalisation
  (ANLS is reported as a secondary, partial-credit measure);
* currency, invoice number: identical after upper-casing (and removing spaces
  for invoice numbers);
* empty values: an empty gold value is matched only by an empty prediction.

Reported metrics:

| metric | definition |
|---|---|
| field accuracy | correct fields / all fields (empty gold values included) |
| field precision / recall / F1 | over non-empty values: correct non-empty predictions / non-empty predictions, / non-empty gold values |
| document accuracy | share of documents with all 12 fields correct |
| hallucinated | non-empty prediction where the gold value is empty |
| invalid format | prediction that cannot be parsed in canonical form |

plus breakdowns by locale, layout, date style, currency style and number of
VAT rates.

## 5. What the benchmark does and does not show

* It isolates **locale handling and normalisation** on clean, realistic
  layouts. Results transfer to real invoices only partly: real documents have
  more layouts, multi-page tables, logos, stamps, handwriting and much worse
  scans.
* The **text track** is fully solvable: a keyword/regex system written for
  these documents reaches 100 % (see the report). Treat that baseline as a
  proof that the labels are consistent with the documents, not as a
  competitor. The interesting question is how *general* systems — LLMs, VLMs,
  commercial document AI — perform without template knowledge.
* The **scan track** adds OCR errors; it separates systems by robustness to
  recognition noise in digits and separators.
